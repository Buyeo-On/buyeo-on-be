# ADR-016: 이월 포인트는 만료 시각을 두지 않는다

- **상태:** 승인됨
- **결정일:** 2026-09-08

## 맥락

`다음에 이어서 쓰기`로 이월한 포인트는 정산 완료 시각부터 240시간 뒤에 만료되어 차감됐다. 만료 확정은 정기 작업과 포인트 조회·변경 선반영 두 경로로 이뤄진다. 프로덕션에서 유효기간 자체를 잠시 없애야 하고, 스케줄러만 끄면 조회·미션 보상 시점에 만료가 그대로 적용된다. 약관 개정과 앱 화면은 이 결정의 운영 전제이며 백엔드 스키마·API 계약과는 별 트랙이다.

## 결정

- 새 `CARRY_OVER` 정산은 `expires_at`을 기록하지 않는다.
- 아직 만료 확정되지 않은 기존 이월분(`expired_at IS NULL`)도 `expires_at`을 NULL로 지운다.
- `point_settlements` CHECK는 240시간 등호를 강제하지 않고, 무기한 이월(`expires_at IS NULL`)과 만료 시각이 있는 행을 모두 허용한다.
- 만료 스케줄러와 조회·변경 선반영 코드는 유지한다. `expires_at`이 있는 행만 기존처럼 `EXPIRE`로 확정한다.
- 이미 `EXPIRE`로 차감된 포인트는 복원하지 않는다.
- 정산 미리보기의 `carryOverDurationHours`는 `0`이고, 정산 응답의 `expiresAt`은 `CARRY_OVER`여도 null이다.
- 만료 정책을 다시 켤 때는 원래 `settled_at + 240시간`이 아니라 복원 시각부터 240시간을 쓴다. 복원 자체는 이 ADR의 범위가 아니다.

## 결과

- 새 이월분과 미확정 기존 이월분은 기한이 지나도 잔액에서 빠지지 않는다.
- 잔액 요약의 `expirations`는 만료 시각이 현재 이후인 항목만 포함하므로, 현재 정책에서는 빈 배열이다.
- 만료 코드 경로가 남아 있어 복원 때 스케줄러와 선반영을 다시 짜지 않아도 된다.
- 애플리케이션이 240시간을 계속 기록하면 새 정산에 기한이 다시 생기므로 스키마 완화와 정산 코드는 한 릴리스로 올린다.

## 기각한 대안

- 스케줄러만 끄기 — 포인트 조회·변경이 만료 도래분을 선반영하므로 기한이 지난 이월분이 그대로 차감된다.
- `expires_at`을 먼 미래로 밀기 — CHECK가 240시간 등호라서 스키마 변경이 필요하고, 잔액 요약에 가짜 만료 예정가 노출된다.
- 환경별 만료 on/off 플래그 — 정책이 스키마·API·약관에 남는데 테스트 매트릭스만 늘고, 플래그만 켜면 기존 NULL 행은 여전히 만료되지 않는다.
